# תשלום לפני הרשמה: חיבור ל"יש חשבונית"

מפגש עם דמי השתתפות **וגם** קישור לתשלום נרשם רק אחרי תשלום. מי שממלא את הטופס מקבל את שלב התשלום ("עוד צעד אחד: תשלום"),
ולא "נרשמת!". אין שמירת מקום: עד שהתשלום מאושר, ההרשמה לא תופסת מקום ולא נספרת בשום מקום (מכסה, "נשארו X מקומות", רשימת
הכניסה, דוחות, הודעות, ייצוא). כשהתשלום עובר, "יש חשבונית" שולחת הודעה (Webhook מסוג "מסמך נוצר"), ההרשמה נרשמת מעצמה,
והעמוד הפתוח אצל המשתתף מתחלף ל"נרשמת!".

- מפגש חינם, או מפגש בתשלום **בלי** קישור: בלי שינוי (נרשמים מיד, משלמים בכניסה).
- מפגש מלא: רשימת המתנה כמו היום (לא משלמים כדי לחכות).
- אם המקומות נגמרו בין ההרשמה לתשלום: ההרשמה נכנסת לרשימת ההמתנה כשהיא משולמת, ונפתחת משימה "תשלום התקבל ואין מקום פנוי".
- מי שהגיע בלי לשלם נרשם בכניסה כהגעה בלי הרשמה, ומשלם במקום כמו כל מי שמגיע בלי הרשמה.
- הצוות רואה בלשונית "נרשמים" את הסינון "ממתינים לתשלום", ויכול ללחוץ "אישור תשלום" (גיבוי למקרה שההודעה לא הגיעה).
- תשלום שלא נמצאה לו הרשמה ממתינה באותו טלפון נשמר ב"תשלומים שלא זוהו" (בלשונית "נרשמים" של המפגש, ובדוחות ← כספים),
  ושם משייכים אותו להרשמה או מסירים אותו מהרשימה.
- הערה על התשלום (payment_note) מוצגת כמו שהצוות כתב אותה. במפגש עם קישור לא כותבים בה "אפשר לשלם גם במקום".

## איך ההתאמה עובדת (בשרת, בהרשאת service role בלבד)

הטלפון מהקבלה (`customerPhone`, בכל צורה: 05x, ‎+9725x, ‎9725x) → ההרשמה הממתינה האחרונה לאותו טלפון מ-14 הימים האחרונים,
למפגש שעוד לא הסתיים, שהמחיר שלו קטן או שווה לסכום ששולם. נמצאה: מסומנת "שולם" (כרטיס אשראי, האסמכתה היא מספר המסמך)
ונרשמת. לא נמצאה: נשמרת ב"תשלומים שלא זוהו". אותו מסמך פעמיים לא משנה כלום. מסמכים אחרים של אותו חשבון (לא תשלום, סכום 0,
או כשאין מפגש בתשלום שיכול להתאים) לא נשמרים. משאר תוכן ההודעה לא נלקח כלום.

## הקמה בייצור (פעם אחת, האחראי על המערכת)

```bash
# 1) המיגרציה
npx supabase link --project-ref <REF>
npx supabase db push        # כולל supabase/migrations/20261106002700_pay_before_register.sql

# 2) הפונקציה, בלי בדיקת JWT (הספק לא שולח JWT; המפתח בכתובת הוא האימות)
npx supabase functions deploy yesh-webhook --no-verify-jwt

# 3) המפתח הסודי: ארוך ואקראי, נוצר במחשב שלכם ולא נשמר בשום קובץ במאגר
KEY=$(openssl rand -hex 32)
npx supabase secrets set YESH_WEBHOOK_KEY="$KEY"
echo "$KEY"                 # מעתיקים פעם אחת להגדרה ב"יש חשבונית", ולא שומרים בצ'אט או בקובץ

# 4) בדיקה: אמור לחזור {"ok":true}
curl -s "https://<REF>.supabase.co/functions/v1/yesh-webhook?key=$KEY"
```

5. ב"יש חשבונית": הגדרות ← Webhooks (או "חיבורים") ← הוספת Webhook מסוג **"מסמך נוצר"**, ובכתובת:
   `https://<REF>.supabase.co/functions/v1/yesh-webhook?key=<המפתח>`
6. במערכת: הגדרות ← יעדים וכללים ← "תשלומים: חיבור ל"יש חשבונית"" מציג את הכתובת **בלי** המפתח. אחרי התשלום הראשון מופיע
   שם "מחובר" עם מועד ההודעה האחרונה.

החלפת מפתח (אם דלף): מריצים שוב את שלב 3 עם מפתח חדש ומעדכנים את הכתובת ב"יש חשבונית". המפתח הישן מפסיק לעבוד מיד.

## תשובות הפונקציה

| מקרה | תשובה |
|------|--------|
| בלי מפתח או מפתח שגוי | ‎404 `{}` (בלי פרטים) |
| גוף מעל 32KB | ‎413 |
| יותר מ-300 קריאות ב-10 דקות מאותה כתובת | ‎429 |
| GET עם המפתח | ‎200 `{"ok":true}` (בדיקת הקמה, לא נוגע בנתונים) |
| POST עם המפתח | ‎200 `{"ok":true,"result":"matched"|"unmatched"|"duplicate"|"ignored"}` |
| מסד הנתונים לא זמין | ‎500 (הספק יכול לנסות שוב) |

הגוף יכול להיות JSON או form-encoded. נקראים רק השדות `docNumber`, `docType`, `price` (מספר או מחרוזת; הסכום הכולל),
`customerPhone`, `customerName`, `date`, מתוך `ReturnValue` או מהרמה העליונה.

## פיתוח מקומי

```bash
cp supabase/functions/.env.example supabase/functions/.env   # ערך מקומי מזויף, הקובץ לא נכנס ל-git
# משנים את הערך לכל מחרוזת אקראית של 32 תווים ומעלה
npx supabase functions serve                                 # מגיש את staff-admin ואת yesh-webhook עם הסוד המקומי
```

הבדיקות (`tests/api/pay-first.test.ts`, `tests/e2e/payments.spec.ts`) קוראות את המפתח המקומי מהקובץ הזה ושולחות הודעות
לדוגמה לפונקציה המקומית.
